### R01 / F17：配置校验存在，初始化顺序不正确（高优先级，已复现）

`app/main.py:5` 先导入 routes/database，再在 create_app 中调用 `prepare_config()`（第 31 行）。`app/database.py:10` 导入时就读取 DATABASE_URL 并创建 engine；`embedding_service.py:208` 同样导入时固定重排开关。

在临时目录、独立 Python 子进程里创建测试 `.env`：DATABASE_URL=sqlite:///./expected.db、CROSS_ENCODER_ENABLED=1。导入应用后的输出：

```text
env_database = sqlite:///./expected.db
engine = sqlite:///./runtime/data/app.db

```

环境变量看似正确，实际数据库和重排开关已经提前固定。可能读写错误的库，所以这是功能错误，而非文档问题。显式在启动前 export DATABASE_URL 可以避开数据库这一项，但不能证明 `.env` 路径已经修好。

建议：在任何依赖配置的模块初始化前加载配置，或让 create_app 明确创建并注入 engine/settings；不要再加第二套配置读取器。验收必须用独立进程验证真实 engine URL 与功能开关，不只测试 load_dotenv 本身。工作量中，收益高。

### R02 / F10：空 supporting_evidence 绕过引用护栏（高优先级，已复现）

`app/llm/citation_guard.py:70` 只遍历已有条目；列表为空时没有任何 unverified_reasons，后续降级不执行。模型 schema 允许空列表。

探针输入：一个根因，confidence=0.99、supporting_evidence=[]。结果仍为 0.99，warnings=[]。

建议：有根因但无支持证据时明确降级/拒绝；无根因的合法弃答单独处理。增加客户端→护栏→API 的回归。工作量低到中，收益高。

另一个机制限制：`[E1]` 存在只证明引用编号有效，不证明句子受 E1 支持。向护栏提供 `[E1] The database was deleted by an attacker.` 也会通过；护栏只接收材料数量，本来就无法验证语义。不能据此宣称防住所有幻觉。可用人工标注的矛盾/伪归因样本评估语义支持，不必立刻再加模型层。
