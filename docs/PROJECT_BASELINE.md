## 2. 项目结论与边界

当前最需要修改的是**诊断结果一致性、证据可追溯性和评测有效性**。模块已经足够支撑完整展示项目，增加新工具或另一套框架不能解决这些问题。

固定定位：面向工程师的故障诊断 Copilot，以日志和事故为中心，输出有来源的根因假设、影响范围、排查建议和执行记录。根因是假设，历史相似案例是参考，置信度暂不是经过校准的正确概率。

主链路：日志接入 → 事故识别/创建 → 分析任务 → 规则与取证 → Runbook/历史案例检索 → 结构化诊断 → 持久化/展示 → 人工反馈与离线评测。

默认不扩展到自动回滚、数据库切换、执行生产命令、通用聊天助手、完整 APM 平台和复杂多租户 SaaS。用户明确改变目标时，记录新范围、理由与验收后调整计划。

README 负责快速开始，DESIGN 保存设计背景，KNOWLEDGE_GUIDE 解释概念。本文件维护当前状态；历史规划不能直接当成“尚未实现”的证据。

### 4.2 隔离探针

探针使用内存 SQLite、注入客户端/集合或 mock patch，没有改动运行数据库。

| 场景 | 实测结果 |
|---|---|
| 同一个 job 调用两次 run_job | 产生 2 个 AnalysisRun |
| 持久化 Trace 时注入异常 | job=failed，但仍留下 1 个不完整 AnalysisRun |
| 同服务两批错误，第一批分析未执行 | 生成两个 Incident 和两个 job |
| 昨天的错误日志触发计数，库内有今天的 3 条错误 | 计为 4 条并触发阈值 |
| Agent 第一轮直接诊断 | 工具调用 0 次，证据为空，仍执行终止回调 |

| 给不存在的 analysis ID 写反馈 | 默认 SQLite 下写入成功，形成孤立引用 |
| 向量集合数量等于来源数量 | 直接返回，未读取内容或调用 embedding；替身验证控制流 |

## 5. 问题清单与验收条件

P0：本地正确性/结果完整性阻断，先修；P1：可信度或持续运行重要问题；P2：维护与增强。安全项另标真实数据/共享部署前阻断，不把本地演示写成已发生安全事故。

“已复现”表示执行了探针或评测；“代码确认”表示控制流直接可见；“待实测”表示尚未做运行验证。**所有条目初始状态：待修复。** 行号属于审查快照，后续请按函数复核。

### F01 · P0：进度提交破坏分析结果的原子性

- 证据：`app/services/analysis_service.py:279` flush AnalysisRun 后发送 persistence 进度；`app/services/analysis_job_service.py:71` 在同一 Session commit。
- 后果：证据/Trace 写入失败时 rollback 无法撤回已被进度回调提交的结果，“最新分析”可能拿到半成品。**已复现，置信度高。**
- 修改：进度更新不得隐式提交业务结果；调整最后一次进度时机或明确事务归属，确保结果、证据、Trace 原子提交。SQLite 下不要简单另开写事务造成锁冲突。
- 验收：证据和 Trace 写入处注入失败，无可见半成品；任务失败可追踪；成功结果关系完整。
- 工作量中（跨 service 和事务测试）；收益高（所有后台分析经过此路径）。

### F02 · P0：任务不幂等，缺少可靠恢复

- 证据：`analysis_job_service.py:31` 不原子领取 pending 状态，直接设 running；API 使用进程内 BackgroundTasks；`app/main.py` 无恢复逻辑。
- 后果：同 job 重跑产生重复结果（**已复现**）；进程退出可能留下 pending/running（代码确认，重启实测待做）；初始进度提交还在 try 外。
- 修改：数据库条件更新领取任务；成功任务重入返回已有结果；定义重试次数、超时和过期任务处理。先修状态契约，再按部署需求决定是否引入独立 worker。
- 验收：重复/并发执行同 job 最多一个有效结果；中断状态能回收或明确失败；初始提交异常有处理。
- 工作量高（执行、恢复跨层）；收益高（防重复调用、悬挂和费用浪费）。

### F03 · P0：自动去重依赖尚未生成的分析结果

- 证据：`incident_detector.py:68` 找到同 issue type 的 AnalysisRun 才认作同类；`automatic_incident_service.py:25` 创建事故、任务分开提交。
- 后果：首次分析未完成，持续日志继续创建同类事故。**顺序探针已复现，不需并发。** 并发先查后建另有竞态风险。
- 修改：创建 Incident 时保存 source、初步类型/聚合键与窗口；去重不依赖未来诊断。明确事故与任务的一致性边界，增加数据库冲突处理。
- 验收：同窗口同类错误在 pending/running 时复用事故；不同故障不误合并；同名服务并发注册有稳定返回。
- 工作量高（模型、迁移、检测、事务）；收益高（自动接入热路径）。

### F04 · P0：事件时间窗口不一致，输入时区未统一

- 证据：`incident_detector.py:55` 计数只有下界，而类型推断有上界；`analysis_service.py:130` 手动事故无上界，自动事故按创建时间截止；`:136` 通过标题前缀识别来源。日志写入未显式将带时区输入统一 UTC。
- 后果：历史日志被未来记录凑够阈值（**已复现**）；旧手动事故重分析可能混入后续故障；晚到日志时间与事故创建时间不一致。输出转北京时间不等于存储语义规范。
- 修改：区分 event_time、received_at、incident window；明确查询起止和开闭边界；输入归一 UTC，无时区输入约定清楚；source 字段代替标题判断。
- 验收：乱序/晚到/未来时间、边界同刻、UTC 与 +08:00 同一时刻、同服务连续不同事故、手动重分析有回归。
- 工作量高（模型、多条查询）；收益高（决定诊断输入）。

### F05 · P0（Agent）：必要取证步骤只写在提示词里

- 后果：零取证也可进入诊断（**调用路径已复现，未评估真实模型答案**）；重复调用只由 prompt 禁止，工具失败成为文本后继续。
- 修改：代码记录成功执行状态，校验诊断前置条件；未知动作明确报决策错误；强类型参数及限额；不足时返回 insufficient_evidence，不用增加 MAX_STEPS 掩盖。
- 验收：首步结束、未知动作、重复参数、工具异常、非法 top_k、预算耗尽都有明确行为。
- 工作量中（Agent、测试）；收益高（防无证据诊断）。

### F06 · P1：Agent 查询未传入检索器，证据来源混用

- 证据：`analysis_service.py:473` 两个检索闭包接收 query 但未使用；`:484` 将 investigation_notes 包成 `id=0` 日志传给 LLM；notes 来自工具统计和摘要。

- 修改：增加接受 query 的公开检索方法；原始日志、派生观察、历史参考分别带类型和来源 ID；结论只引用本次已收集来源。
- 验收：query 变化真正改变检索输入；调查证据可回溯 log ID；统计说明不冒充原始日志。

- 修改：区分检索、生成、运行回归；增加具体案例 ID、引用有效率、证据精度、弃答率、负例误报率、降级率与成本；调参与保留评测样本分离，人工复核标签。
- 验收：列配置/有效后端、模型/语料/数据集版本、成功错误数；全部 fallback TF-IDF 的实验不能当多个模型效果对比。
- 工作量中（标注、指标）；收益高（避免优化错误目标）。

### F13 · P1：Dashboard 可显示错误事故或旧结果

- 证据：`templates/dashboard.html:79` 异步返回直接覆盖全局 loadedAnalysis，不检查 selectedIncident；404 直接返回，不清旧诊断；`:75` 只在未缓存时加载，不按 run ID 更新。
- 后果：快速 A→B 切换时 A 慢响应可能覆盖 B；无结果时残留旧内容；同事故再次分析后仍显示旧结果。**代码确认，浏览器实测待做。**
- 修改：请求代次/取消和 ID 校验，按 run ID 缓存；切换清空，定义 loading/empty/failed/degraded 状态。
- 验收：响应逆序、404、重试、新 run、断线重连均不混淆身份；统计卡说明“最近 50 条”或全局口径。
- 工作量中（局部 JS、交互验证）；收益高（防依据另一事故行动）。

### F14 · P1：SSE 全量查询与模拟流式阻塞

- 证据：`app/api/routes.py:78` 每连接每秒全量查询再 `[-50:]`；`/analyze/stream` 在 async 路由里同步完成分析后再 sleep 播放。
- 后果：成本随总日志和连接数增长；慢分析阻塞事件循环；“流式”不代表真实进度。**代码确认，吞吐量未压测。**
- 修改：数据库 limit/游标、合适索引、输入上限；主交互复用 job 进度。保留模拟接口需标明回放，需要真流式再让实际步骤发事件。
- 验收：最新记录查询有数据库限额；慢模型不阻塞健康请求/SSE；不增设第二套执行器。
- 工作量中；收益高（持续演示与数据增长）。

### F15 · P1：反馈存在性未校验，正向过滤忽略正确性

- 证据：`feedback_service.py:10` 直接 upsert；`app/database.py` 未启用 SQLite 外键检查；正向查询只看 rating，未看 is_diagnosis_correct。
- 后果：不存在 analysis ID 可写反馈（**已复现**）；高评分但判错也列为正向。当前未接自动学习，不宣称已污染检索库。

- 验收：不存在对象、并发重复反馈、rating 高但 incorrect、旧库迁移行为明确。

### F16 · 真实数据/共享部署前阻断：缺少身份边界

- 证据：`app/api/routes.py` 日志写入、事故创建、分析触发、结果/事件读取无身份依赖，main 无身份中间件。

- 验收：未授权拒绝，日志/错误信息不输出凭据，写入大小和频率有限额。

## 9. 防止过度新增与偏离方向

- 先修失败场景再论证新能力；无明确用户需求或可验证问题，不增加抽象层。
- 不为好看指标删除 hard cases、随意放宽标签，或把 fallback 当目标后端成绩。
- “工具声明了”“返回 JSON”“测试通过”不等于真实取证、可信诊断或可生产部署。
- 检索、证据选择、响应整形明确归属；迁移时说明旧路径撤除条件，不长期维护两套主链路。
- 历史案例、工具摘要与当前日志分开，不让未经人工确认的评分自动成为新知识。
- API/DB/诊断 schema 变化考虑旧库与页面，不只修返回 JSON。
- 保持 FastAPI + SQLAlchemy + SQLite 原型架构，实际并发/任务/部署需求证明必要时再迁移设施。
- 用户批准新方向可以改变计划，每次记录原因、影响、验收和回退，不依赖聊天上下文记忆。

通过根目录 `AGENTS.md` 提醒支持该文件的编码助手先读，README 提供人工入口。**未添加启动钩子，业务程序不会自动阅读 Markdown，也不能保证不支持 AGENTS.md 的工具执行。** 换工具时手动要求先读本文件。
