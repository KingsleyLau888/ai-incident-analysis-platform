## 重要问题

### 1. 简历和面试稿仍有超出实现的表述（投递前应纠正）

- `RESUME_DRAFT_20260912.md:20` 把编号校验写成拦截模型编造。`app/llm/citation_guard.py:47` 只接收各类材料数量，不能检查引用原文是否支持结论；也没有对报告每个字段做事实核验。本轮构造借用合法 `[E1]` 的编造文字，置信度仍为 0.99、warnings 为空。
- `RESUME_DRAFT_20260912.md:33` 与 `INTERVIEW_GUIDE_20260913.md:47` 把 87.59% 叫证据引用率。`app/services/llm_judge.py:211` 与 `eval/run_eval.py:678` 表明它是 Judge 返回分值的平均值，不是正确引用数量的比例。历史前后对比还改变了裁判可见材料，不能当作相同测量条件下的纯质量提升。
- `RESUME_DRAFT_20260912.md:23` 的“断电恢复”超出验证。`analysis_job_service.py:141` 实际为启动时 pending 重派发、running 标失败，不能从中断步骤续跑，也未证明断电无损。
- `INTERVIEW_GUIDE_20260913.md:218` 的“预计算后查询只做向量查找”错误。`vector_store.py:315/344` 仍编码查询，省掉的是重复文档编码。后续简历截图补核找到历史原始表 `runtime/audit/2026-09-09-preopt/rag_ablation_report.md`：dense 377.47ms、ChromaDB 16.31ms、两组 Top-1 均 81.82%。数字有历史依据，可明确限定为历史单查询检索基准、不含初始化/索引构建；本轮未复测，不能说成当前全流程性能。历史报告位于 Git 忽略目录，交接应保留可访问证据。

最小处理是修正正式投递文本，不要求改业务代码。工作量低，收益高：面试时这些说法可以直接被源码追问推翻。个人贡献按实际承担描述，代码存在不能证明全部由本人独立设计。

### 2. Agent 决策失败后静默回退，执行标记失真（本轮新增，F09 待修复）

位置：`app/agent/react_agent.py:444` 的 `_llm_decide` 捕获异常后直接调用 `_deterministic_decide`，不记录异常或回退；`AgentResult.provider` 按是否持有客户端标为 `react_llm`。`analysis_service.py:651/693` 又把这个标记用于分析计划和 Trace。

隔离注入：假客户端的 `decide_action` 连续 5 次抛出 RuntimeError。结果完整执行 search_logs → detect_signals → retrieve_runbooks → retrieve_similar_incidents → generate_diagnosis；provider 仍是 `react_llm`，步骤观察没有决策失败说明。

影响：动态决策不可用时仍能生成结果，但 Trace 无法区分真正的模型选择与固定流程回退；不能把这些执行算作 Agent 成功，也不能宣称所有模型降级都已完整记录。这与最终诊断调用的 `mock_fallback` 记录是不同路径。

建议：后续记录每步 decision provider、失败原因和回退次数，区分混合/固定回退；不建议为此更换框架。工作量中（Agent 返回契约、Trace 和回归需要同步），收益中（影响决策故障时的可追溯性）。校招固定 pipeline 展示可暂缓；若简历核心卖点是 Agent 可靠性，应优先修这一处。本轮按用户意愿只审查。

### 3. 现有评测只能支持开发回归与局部检索成绩（F11/F12）

本轮 27 例中 18 例通过全部组合条件、9 例失败。Runbook Top-1 88.89%、Recall 84.57%、P@3 74.07%；规则类型/严重程度匹配率均为 92.59%。

`eval/run_eval.py:485` 的 passed 组合类别、严重程度、证据关键词与检索来源召回，未人工判定根因正确性；历史事故 Top-1 比较的是 issue_type，不是具体事故身份。88.89% 不能叫诊断准确率，100% 不能叫精准匹配历史事故。

`_run_case` 直接创建日志和手动事故，再调用分析服务；日志级别按 message 是否含 error 设置。它没有覆盖真实日志接入、自动触发/去重和后台任务调度，也不忠实保留真实日志级别。这些路径须依赖其他测试和接口冒烟，不能用这 27 例统一背书。

数据为项目内模拟集，且用于优化与验收，未建立独立保留集或真实生产对照。Judge 同模型自评与小样本限制仍在；真实模型历史“未检出”不能写成零幻觉保证。无需追满分才能投递，但应准确限定指标对象与数据范围。

## 可暂缓的问题

1. **规则误报与证据遗漏仍在。** 正常缓存/内存警告案例被分成 cache_issue/memory_issue；矛盾信号、发布异常、队列和 DNS 案例有证据关键词漏选。这里是分析分类误报，不等于 WARN 日志必然触发自动事故。`detector.py:151` 按词面加权，没有充分的否定语义与弱信号拒判；不能宣传通用根因识别。
2. **硬类型过滤限制跨类型召回。** `runbook_retriever.py:394` 在 hard 模式只选同类 chunk。配置密钥、网络策略等可能被初步分类限制。当前集消融支持保留 hard，但不证明它普遍最优；Recall 仍未达到原定 85% 门槛。不必为差 0.43 个百分点继续改项目。
3. **单进程能力有明确边界。** 进程内服务锁、BackgroundTasks、启动时 running 清场和内存限流不支持多 worker 可靠协调。SSE 快照仍是每连接定时查库；当前无需为简历补 Redis/Celery、RBAC、多 Agent 或自动修复。
4. **交接文档有陈旧描述。** README:99 仍说页面全部带锁，实际静态页面壳开放、数据接口带锁；requirements 虽以注释区分“可选”，一次安装仍会装重型检索依赖，且已记录开发 venv 与声明版本不同。此次没有新建环境安装验证，不承诺全新机器一键复现。

## 投递判断

在本轮审查范围内，可以作为**个人 AI 应用/后端校招项目**投递，未发现需要推翻架构或暂停所有投递的主链路阻断。它已有从日志到诊断、证据持久化、任务状态和离线评测的可验证实现；上述结论不是生产就绪或全部代码无缺陷的保证。

最小行动：改准简历；掌握一次完整调用链；准备成功、失败与模型不可用三个案例。Agent 新缺口允许在固定 pipeline 定位下明确记录后暂缓，不要用“所有降级完整记录”包装现状。

推荐正式简历压成三条（个人贡献据实调整）：

- 基于 FastAPI、SQLAlchemy 和 SQLite 实现日志接入、自动事故识别、后台分析与诊断展示，结合规则与 Runbook/历史案例检索生成结构化根因假设。
- 优化查询构建与手册分块类型标注，在项目内 27 例模拟故障集上，将 TF-IDF 配置下 Runbook Top-1 从历史基线 55.56% 提升至 88.89%，Recall 从 77.16% 提升至 84.57%；后值本轮复现，前值来自历史实验记录。
- 实现证据编号追溯、无效引用降级、任务原子领取与结果事务提交，建立自动化回归与离线评测流程，本轮 235 项测试通过。

投后端岗位应能讲清事务、条件更新、唯一索引、单进程恢复边界与 SSE；投 AI 应用岗位应能讲清分块、查询构建、RRF、过滤取舍、引用校验边界和评测定义。当前证据不足以按模型训练/算法研究项目包装。
