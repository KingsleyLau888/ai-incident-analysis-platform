## 应在面试前纠正的概念与表述

### 1. 检索命中率、规则分类、诊断正确性必须分开

`analysis_service.py` 保存的 issue_type / severity 来自规则检测；`eval/run_eval.py` 分别比较规则类别、严重程度、证据关键词、手册来源与历史事故类型。整体 passed 是这些条件的组合，不是人工判断根因正确。

88.89% 是 27 个案例的 Runbook 首条来源命中率。当前复测后端为 TF-IDF，不应把它接在 ChromaDB 的介绍后，暗示向量库带来了同样提升。历史事故的 Top-1 按类别匹配，不能解释成精准找到具体历史事故。

可写：在项目内 27 例模拟故障集上，优化查询构建与手册分块类型标注，使 TF-IDF 配置下 Runbook Top-1 由 55.56% 提升至 88.89%。前值依据历史优化记录，后值本轮复现。

### 2. 87.59% 是 Judge 平均评分，不是引用正确率

`app/services/llm_judge.py` 的 evidence_grounding 是模型返回的 0–1 分值，`eval/run_eval.py` 对其求均值。它不是“正确引用数 / 总引用数”。

历史对比同时修改了诊断侧与裁判可见资料，因此 55.19%→87.59% 不能当作同一把尺子测出的纯模型能力提升。修复前的 92.59% 幻觉标记主要包含裁判测量缺陷，也不能宣传为把真实幻觉率从 92.59% 降到 0。

建议简历删除这组易误解的前后对比，改写为：建立开卷 LLM-as-Judge 评测，定位并修正裁判缺失检索上下文导致的误判。面试再解释小样本与同模型裁判的偏置。

### 3. 引用护栏没有实现事实核验

`app/llm/citation_guard.py` 核对引用编号是否存在，对空引用和越界引用降级；它没有比对引用文字和原始材料的语义，也不覆盖报告每个字段。

独立探针：构造引用 `[E1]` 的无依据文本，传入 evidence_count=1。结果 confidence=0.99、warnings=[]。这个函数只接收材料数量，本来就不具备语义核验所需的原文。

可写：实现证据编号追溯、无效引用校验和置信度降级。不可写：强制每条结论可信、拦截所有编造、零幻觉。无需为了写简历而新建复杂事实核验系统，诚实界定边界即可。

弃答也有明确边界：真实诊断客户端在所有材料为空时弃答；有手册不代表已有足够事故事实，不能把“有材料”说成“证据充分”。

### 4. 文档向量预计算之后，查询仍要编码

`app/services/vector_store.py:315` 与 `:344` 仍调用 `self.embed_fn([query_text])`。正确解释是减少重复文档编码，再对在线查询编码和检索。

用户已有 `docs/INTERVIEW_GUIDE_20260913.md:218` 的“查询时只做向量查找”不准确。本轮未修改该用户文件，学习时请以本条纠正。

377ms→16ms 本轮未核实同口径原始性能证据。已读取的正式四后端历史报告记录的是全流程平均耗时，其中 dense 2570.23ms、ChromaDB 169.33ms；两组数可能对应不同计时范围，不直接判定旧数字虚假，但不能混用。简历暂去掉 377→16，或先找齐测量代码、阶段范围、冷暖启动、样本与硬件记录。

### 5. 固定流程与 Agent 分支是两种执行模式

`app/agent/analysis_mode_router.py` 决定 pipeline / agent；未显式配置时 `_requested_analysis_mode()` 返回 auto，无真实 Agent 客户端则走 pipeline。本轮评测显式使用 pipeline。

Agent 有真实的工具白名单、步数预算、成功取证前置条件、重复调用与参数约束，不是只换一个名字。但不能用 pipeline 成绩证明 Agent 更准，也不能说所有请求都经过动态调查。

可写：实现稳定的规则与 RAG 分析流程，并提供受限 ReAct 调查模式；尚未证明 Agent 相对固定流程的质量收益。规则辅助分类不违背 Agent/RAG 的定义。

### 6. 恢复能力、Trace 与反馈也应按实现说明

- `analysis_job_service.recover_interrupted_jobs`：pending 重新派发，running 标记失败；仅针对单进程。不是从中断步骤继续执行，也不是可靠分布式队列，更不是已验证的断电无损恢复。
- Trace 是步骤、工具结果与降级记录，支持排查执行过程，不是模型内部推理正确性的证明。
- 反馈已能记录，但未自动更新模型或知识库，不能称持续学习闭环。
- 模型失败可降级到 mock_fallback，Trace 有说明；演示真实模型能力前应核实实际 provider，避免把模板输出当作模型输出。

## 合理的项目局限，不必为此推倒重做

1. 固定 27 例模拟集规模小，且用于优化和验收；适合作为开发回归集，尚不能证明泛化。没有独立保留集不是禁止写简历的理由，但不能宣传生产效果。
2. 两类良性警告可能被规则误分；矛盾信号和弱证据选择仍有问题。现有 9 个失败案例已显式记录，不需要追到全过才面试。
3. 硬类型过滤会排除跨类型手册，属于明确的召回代价；“hard 在当前集更好”不等于所有场景最优。
4. SQLite、进程内后台任务和单钥匙鉴权适合受控单机展示，没有必要仅为简历增加 Redis、Celery、多租户或多 Agent。
5. 当前没有证据支持真实生产流量、自动根因确定、自动修复或生产高可用等宣传。
